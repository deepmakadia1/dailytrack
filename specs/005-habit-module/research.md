# Research: Habit Module (Phase 2, T2.1–T2.4)

**Feature**: [spec.md](spec.md) · **Plan**: [plan.md](plan.md) · **Date**: 2026-10-18

Each decision is written as Decision / Rationale / Alternatives considered. The Technical Context of
the plan had no open `NEEDS CLARIFICATION` items. Product questions were settled in the spec's
Clarifications (Q1–Q2). The items below settle how to build it.

---

## R1. Packages

**Decision**: add one direct dependency. Everything else the user named is already direct.

| Package | Version | Why | Layer |
| --- | --- | --- | --- |
| `timezone` | ^0.11.2 | Zoned scheduling for habit reminders (spec §2 "Notifications", user request). Already in `pubspec.lock` as a transitive dependency of `flutter_local_notifications` (`flutter pub add timezone --dry-run` on 2026-10-18: "from transitive dependency to direct dependency"), so it adds no code size | `core/notifications/` only |
| `flutter_local_notifications` | ^22.3.2 (existing) | Scheduling, cancel, boot rescheduling | `core/notifications/` only |
| `share_plus` | ^13.3.1 (existing) | Share the streak card and heatmap images | `core/share/` only |
| `fl_chart` | ^1.2.0 (existing) | HAB-03 weekly bar chart | `features/habit/presentation/widgets/charts/` only |
| `path_provider` | ^2.1.6 (existing) | Temporary PNG file for sharing | `core/share/` only |
| `clock` | ^1.1.3 (existing) | Injected time in the streak engine and controllers | all layers (pure Dart) |

**Device time zone**: the `timezone` package cannot read the device's IANA zone. The
`flutter_local_notifications` README suggests `flutter_timezone`, which is **not** on the §2 list.
Instead, `MainActivity.kt` answers one method on a `dailytrack/timezone` `MethodChannel` with
`java.util.TimeZone.getDefault().id` (about 10 lines). If the channel fails or returns a zone the
`timezone` database does not know, reconciling is skipped and the reminders already scheduled are
left alone, so nothing fires at a wrong UTC-based time; the next app open tries again.

**Rationale**: Constitution VII: no packages beyond §2 unless justified. A 10-line channel is smaller
than a plugin dependency and has no version churn.

**Alternatives considered**: `flutter_timezone` (extra plugin, not in §2); guessing the zone from
`DateTime.now().timeZoneOffset` (ambiguous; wrong around DST changes for non-Indian users).

## R2. Schema v3 → v4

**Decision**: schema version 4 adds 3 tables owned by the habit feature
(`lib/features/habit/data/tables/`): `habits`, `habit_schedules`, `habit_entries`. No existing table
changes. `from3To4` creates the tables and indexes only; v1 and v2 databases run the earlier steps
first. `drift_schemas/app_database/drift_schema_v4.json` is generated by
`dart run drift_dev make-migrations`, and the migration test upgrades v1, v2, and v3 databases
**with data** and checks every existing row is unchanged and the seed markers are kept. Details in
[data-model.md](data-model.md).

**Rationale**: Constitution III requires a migration and a migration test for every schema change.
Pure additions need no table rebuild, so the step is low-risk.

**Alternatives considered**: storing schedule history as JSON on `habits` (no constraints, hard to
query, not migration-friendly); a separate habit database (breaks atomic writes with `unlocks` and
settings and the single `SchemaVerifier`).

## R3. Schedule and target history

**Decision**: `habit_schedules` keeps one row per (habit, effective-from date). Creating a habit
writes version 1 effective from the start date. Saving an edit that changes schedule type, weekdays,
times per week, or target writes a version effective from **today** (local); if a version for today
already exists it is updated in place (Edge Cases: several changes on one day keep the last). The
`habits` row mirrors the newest version so lists and reminders read one row.

The engine picks, for a day `d`, the newest version with `effectiveFromKey ≤ d`, or the oldest
version when `d` is before all of them (this covers a start date edited to an earlier date). Changing
the start date only moves the first version's effective date when it would otherwise be after the new
start.

**Rationale**: HAB-02 requires "streaks are recalculated using the new schedule from the change date
onward". Mirroring keeps HAB-01 and reminders on single-row reads.

**Alternatives considered**: recomputing past days with the new schedule (contradicts HAB-02); a
copy-on-write of the whole habit row (needless duplication of name, icon, reminders).

## R4. Entry rows: one physical row per habit and day

**Decision**: `habit_entries` has a **full** unique index on `(habit_id, date_key)`, so there is at
most one physical row per habit and day, live or soft-deleted. "Create" is an upsert that clears
`deleted_at`; "delete" sets `deleted_at`. A live row exists exactly when the day has value > 0, a
freeze, or a note (Edge Cases). Undo restores the previous snapshot (value, freeze, note,
`deleted_at`) captured by the write.

**Rationale**: satisfies the HAB-01 criterion ("creates or deletes the `habit_entries` row") with soft
delete (Constitution III), and avoids an unbounded pile of deleted rows from repeated toggling.

**Alternatives considered**: partial unique index among live rows plus a new row per toggle (row
churn on the hottest path); hard delete (violates soft delete).

## R5. Dates and weeks in the domain

**Decision**: a small pure-Dart `LocalDate` value type in `features/habit/domain/dates.dart`
(year, month, day; `fromKey`/`key` via `DateKeys`; `addDays`, `difference`, `weekday`,
`startOfWeek(firstDayOfWeek)`). Day arithmetic runs on `DateTime.utc(y, m, d)` so daylight-saving
transitions in other zones never produce 23- or 25-hour days. "Today" is
`LocalDate.fromDateTime(clock.now())` (local). The week start comes from settings
`firstDayOfWeek` (default Monday) and is passed into the engine.

**Rationale**: Constitution III (habit days are local `yyyy-MM-dd` keys); exact day math for
streaks; one type for engine, controllers, and tests.

**Alternatives considered**: raw `DateTime` local midnights (DST bugs); integer day numbers only
(less readable tests).

## R6. Streak engine (pure domain)

**Decision**: `StreakEngine` in `features/habit/domain/streaks/` takes a `Clock` (package:clock) and
`firstDayOfWeek`, and works on a `HabitHistory` (kind, start date, schedule versions, entries by
date). It exposes:

- `dayStatus(date)` → `done | partial | missed | freeze | unscheduled | beforeStart | future | pending`
  (`pending` = today, scheduled, not yet done).
- `summarize()` → `StreakSummary(current, best, completionRate30, totalCompletions, unit)` where
  `unit` is days or weeks.
- `isScheduledOn(date)`, `weekProgress(date)` (done count and target for "times per week").

Rules (spec §4, Edge Cases, `docs/spec.md` §4 as amended):
- "Scheduled": daily → every day ≥ start; specific weekdays → selected weekdays ≥ start; **times per
  week → every day ≥ start** for `isScheduledOn`, freezes, and Skip today. The HAB-01 "listed as
  scheduled until the week's target is met" rule is a presentation rule computed from
  `weekProgress`, not the engine's `isScheduledOn`.
- Days after today (clock moved back) have status `future` and count toward no statistic.
- Day-based schedules: walk back from today over scheduled days; `done` adds 1, `freeze` adds 0 and
  continues, `missed` stops; today `pending` is skipped. Unscheduled days are skipped.
- Weekly: walk back over weeks; a met week adds 1; an unmet week containing a freeze day adds 0 and
  continues; another unmet past week stops; the current week is skipped while unmet.
- Best streak: one forward pass computing every run with the same rules, max with current.
- Completion rate: last 30 days including today; scheduled days ≥ start; freeze days excluded; today
  counts only if done; whole percent rounded half up; `null` when no countable day. Weekly habits use
  weeks overlapping the window; the current week counts only once met or over.
- Total completions: count of `done` days (any day ≥ start, scheduled or not).

Complexity is O(days since start) per habit; 5 years ≈ 1,830 days.

**Testing**: (a) table-driven cases for every rule and Edge Case, each with an injected
`Clock.fixed`; (b) a reference oracle in `test/` written as the most literal reading of the rules,
compared with the engine over ≥ 100 seeded random histories (SC-002); (c) boundary sets: week starts
Monday/Sunday/Saturday, month and year ends, 29 Feb, start date today/past/future, schedule and
target changes mid-run, the clock at 23:59:59 and 00:00:00.

**Rationale**: the user asked for a pure-Dart engine with an injected clock and exhaustive tests; the
oracle catches rule interactions that hand-written tables miss.

**Alternatives considered**: computing streaks in SQL (untestable without a DB, hard to express
freezes and weeks); caching streaks in columns (stale after back-fill and schedule edits).

## R7. Loading history efficiently

**Decision**:
- **HAB-01 and the Home card** watch active habits plus their entries from `today − 400 days`
  (covers a 365-day milestone, the week strip, and a full year of the weekly rate window). When a
  habit's computed run reaches the window start, its controller loads that habit's full history once
  (`HabitRepository.entriesFor(habitId)`) and recomputes; this is rare and cached per habit until its
  entries change.
- **HAB-03** watches one habit's full history.
- **HAB-04** computes best streak per archived habit from a one-shot full-history read.

Entry reads select only `habit_id, date_key, value, is_freeze` (notes are read separately for the
HAB-03 notes list).

**Rationale**: SC-004 asks for content in under 500 ms with 50 habits × 5 years; streaming 91,000
rows on every check-in would not meet the 100 ms write-to-update budget (SC-003).

**Alternatives considered**: loading all history always (too slow at scale); materialized streak
columns (R6).

## R8. Check-in, freezes, and milestones in one write

**Decision**: every change to a day goes through one domain use case, `HabitDayWriter`, which calls a
single repository method running a Drift transaction:

1. Read the current entry snapshot and the habit's `freezesAvailable` and `celebratedMilestones`.
2. Apply the operation: `toggle`, `setValue`, `increment`, `setNote`, `useFreeze(allowToday)`,
   `skipToday` (= `useFreeze(allowToday: true)` with the "scheduled, not done" check), or
   `restore(snapshot)` (Undo).
3. Freeze rules (`FreezePolicy`, pure): from the freeze card only days 1–3 before today; today only
   via Skip today; never on done, future, or before-start days; count must be > 0. Turning a freeze
   day into a done day refunds one freeze, capped at 2.
4. Load history (R7 window or full), run the engine, and compare the new current streak with
   `celebratedMilestones`; set the bits of every milestone ≤ current with a compare-and-set update
   (`WHERE celebrated_milestones = :old`). Return the highest newly set milestone, if any.
5. Return `DayWriteResult(snapshotBefore, summary, milestone?)`.

After the transaction, the use case asks the reminder scheduler to reconcile that habit (R10).

**Rationale**: the milestone must appear once per milestone per habit even if HAB-01 and the Home
card write at the same moment; compare-and-set inside the transaction guarantees it (the same pattern
as feature 003's budget alerts). Undo needs the exact previous state.

**Alternatives considered**: checking milestones in controllers (duplicate sheets across screens);
storing milestones in settings (not per habit, not in the habit's backup section later).

## R9. Debug freeze grant

**Decision**: `HabitRepository.addFreeze(habitId)` increments `freezes_available` up to 2 (CHECK
constraint plus `WHERE freezes_available < 2`). HAB-03 shows the "Add a freeze (debug)" button only
when `debugToolsAvailableProvider` is true **and** `AppSettings.debugUnlockAll` is true (both
existing core providers). Prod builds bind `debugToolsAvailable = false`, so the button is never
built. Turning the switch off hides the button and leaves granted freezes alone (FR-037).

**Rationale**: Q2 answer; mirrors the future rewarded flow (one grant per action), so T4.4 swaps the
button for PRM-02 without touching the data path.

**Alternatives considered**: treating `FeatureGate.isUnlocked(streakFreeze)` as "has freezes" (the
gate answers "is the feature available", not "how many"; freezes are a per-habit consumable).

## R10. Reminders: scheduling model and "only if not done"

**Decision**: each reminder slot is a **repeating** zoned notification whose **first** fire time is
chosen so that a done day is skipped:

- Daily and "times per week" habits: one notification per reminder index, repeating daily
  (`DateTimeComponents.time`).
- "Specific days" habits: one notification per reminder index **per selected weekday**, repeating
  weekly (`DateTimeComponents.dayOfWeekAndTime`).
- First fire time = the next scheduled occurrence at `HH:mm` local that is on or after the start date
  and, when `remindOnlyIfNotDone` is on, is not on a day that is already done (for "times per week",
  not in a week whose target is already met: the first fire moves to the first day of next week).
- IDs: `stableNotificationId('habit:<habitId>:<index>:<weekday 0–7>')` (FNV-1a, 31-bit), moved from
  `features/expense/data/notifications/` to `core/notifications/notification_ids.dart` so both
  modules share it. All 24 possible IDs for a habit (3 indexes × 8 weekday values) are cancelled
  before rescheduling, so removed slots never linger.

A pure function `planReminders(habit, today, now, doneToday, weekTargetMet)` in
`features/habit/domain/reminders/` returns the list of `PlannedReminder(id, firstAt, repeat)`; the
data-layer `LocalHabitReminderScheduler` turns them into `NotificationService.schedule` calls.

**When reconciling happens**: after every day write that touches today or this week, after saving,
archiving, restoring, or deleting a habit, on `HabitModule.onEnable` and `onAppOpen` (also picks up
time-zone changes and day rollovers), and cancel-all on `onDisable`. Reminders are skipped entirely
when `notificationsEnabled` or the new `habitRemindersEnabled` setting is off or the OS blocks
notifications.

**Reboot**: the plugin's `ScheduledNotificationBootReceiver` reschedules stored zoned notifications
on `BOOT_COMPLETED` and `MY_PACKAGE_REPLACED`; the manifest adds `RECEIVE_BOOT_COMPLETED`, the boot
receiver, and `ScheduledNotificationReceiver`. The next app open reconciles again.

**Exact alarms**: the manifest declares `SCHEDULE_EXACT_ALARM` (user-granted, not the Play-restricted
`USE_EXACT_ALARM`). The scheduler uses `AndroidScheduleMode.exactAllowWhileIdle` when
`canScheduleExactNotifications()` is true, else `inexactAllowWhileIdle`; HAB-02 shows the "may be a
few minutes late" hint in the second case. The app never prompts for the permission in this feature.

**Tap**: payload `/habits` (HAB-01 for today), routed by the existing tap handling, through the lock
redirect when lock is on (feature 003 Open item 3 still applies).

**Rationale**: OS-scheduled notifications cannot check the database at fire time; moving the first
fire past a done day gives "only if not done" without a background job, keeps one stable ID per
habit + reminder index (+ weekday for weekly repeats), and survives reboot through the plugin.

**Alternatives considered**: one-shot notifications rescheduled by a daily workmanager job (stop
firing if the job is deferred; extra background work); scheduling 14 days of one-shots (ID explosion,
up to 42 per habit, and the Android 500-alarm limit with many habits); checking at fire time with a
foreground service (battery and Play policy cost).

## R11. NotificationService additions (core)

**Decision**: extend the existing interface rather than adding a second service:

- `NotificationChannelId.habitReminders` (appended; Android id `habit_reminders`, default
  importance).
- `Future<void> schedule(ScheduledNotification n)`: `n` = `AppNotification` + local wall-clock
  `firstAt` + `RepeatInterval` (`daily`, `weekly`) + `exact` flag.
- `Future<void> cancel(int id)`.
- `Future<bool> canScheduleExact()`.
- `initialize()` also runs `tz.initializeTimeZones()` and sets `tz.local` from the
  `dailytrack/timezone` channel (R1); `refreshTimeZone()` is called by `HabitModule.onAppOpen` before
  reconciling.

Text for habit reminders comes from ARB through `l10nFor(settings.locale)` like budget alerts, and
contains only the habit name and a short encouragement (FR-043).

**Rationale**: one notification owner in core (Constitution II); `FakeNotificationService` gains the
same methods and records scheduled items for tests.

**Alternatives considered**: a habit-specific plugin wrapper (two importers of the plugin, breaks the
existing scan rule).

## R12. Share images

**Decision**: add `ImageSharer` next to `TextSharer` in `core/share/`:
`Future<void> sharePng(Uint8List png, {required String fileName, String? text})`, implemented with
`path_provider` (temporary directory) + `SharePlus.instance.share(ShareParams(files: [XFile(...)]))`.
A shared helper `captureBoundaryPng(GlobalKey, {pixelRatio: 3})` in `core/widgets/share_capture.dart`
renders a `RepaintBoundary`. The milestone share card is an off-screen widget built from tokens
(icon, color, name, streak with unit, app name); the heatmap share captures the HAB-03 heatmap
widget. Widget tests use `FakeImageSharer`.

**Rationale**: user request (share_plus); keeps the plugin behind a core interface like `TextSharer`;
no user data beyond what the card shows (FR-045).

**Alternatives considered**: drawing the card with `dart:ui` `PictureRecorder` by hand (duplicates
widgets); sharing a text-only message (the spec asks for an image card).

## R13. Heatmap, calendar, and chart data in controllers

**Decision**: `HabitDetailController` builds, once per history change, a `HabitDetailViewModel` with:
a `Map<LocalDate, DayCell>` for all days since start (status, intensity 0–4 from
`min(value / target, 1)` in quarters, note flag); `HeatmapModel` (53 columns × 7 rows aligned to the
week start, last 12 months, cells outside the range empty); `CalendarMonth` models produced lazily
from the day map when a page is shown; `WeeklyBars` (12 weeks of completion counts). Builders are pure
functions in `presentation/controllers/habit_view_models.dart`, unit-tested and timed: 365 days in
< 100 ms (actual target < 20 ms on host). The heatmap widget is a single `CustomPaint` with a
`Semantics` summary ("X of Y days done in the last 12 months") and a per-month text list for screen
readers.

`fl_chart` is imported only in `features/habit/presentation/widgets/charts/weekly_bars_chart.dart`,
and the chart is wrapped in `LockedFeatureOverlay` driven by `featureGate.watch(advancedReports)`
(no `onWatchAd`, no `onGetPro`).

**Rationale**: HAB-03 criterion "precompute in the controller"; user request; same pattern as
feature 003's report view models (R12 there).

**Alternatives considered**: 371 individual widgets for the heatmap (slow layout, heavy semantics
tree); computing in `build` (repeats work on every frame).

## R14. HAB-01 week strip and selection

**Decision**: the strip shows the current week (from `firstDayOfWeek`) and can page back exactly one
week. A day is selectable when `0 ≤ today − day ≤ 7`; future days and older days are disabled with
semantics hints. The selected date lives in `HabitsTodayController` state (default today, reset to
today on a day rollover detected at resume). Mini rings show `done / scheduled` for each day of the
visible week, computed from the same R7 window. The notification payload and quick-add open
`/habits` (today).

**Rationale**: makes "back-filling yesterday" possible on the first day of the week (spec
Assumptions) without a date route parameter.

**Alternatives considered**: a rolling "last 7 days" strip (contradicts "Mon–Sun" layout); unlimited
paging (spec limits HAB-01 to 7 days back).

## R15. Routes and HabitModule hooks

**Decision**:

| Path | Screen | Placement |
| --- | --- | --- |
| `/habits` | HAB-01 | Tab 3 root |
| `/habits/add?template=<id>` | HAB-02 new | Root navigator (full-screen modal, above the shell) |
| `/habits/archived` | HAB-04 | Pushed in the Habits branch |
| `/habits/:id` | HAB-03 | Pushed in the Habits branch |
| `/habits/:id/edit` | HAB-02 edit | Root navigator |

Static segments (`add`, `archived`) are declared before `:id`. `HabitModule`: `routes` as above;
`dashboardCard` → `HabitDashboardCard`; `quickAddAction` → label `habit_quickAddCheckIn`, icon
`Icons.check_circle`, location `/habits`; `backupSection()` → `null` (stub until T3.2); `seeders`
empty; `backgroundTasks` empty; `onEnable` and `onAppOpen` → refresh time zone and reconcile all
reminders; `onDisable` → cancel all habit reminders. A habit tap on Home goes to HAB-03 with
`context.push`, which works across branches like feature 003's notification taps.

**Rationale**: spec §5 routes; `TrackerModule` contract unchanged.

**Alternatives considered**: putting HAB-02 inside the branch (spec §5 says full-screen modal);
a `date` query on `/habits` (not needed, R14).

## R16. Templates

**Decision**: `habitTemplates` is a const list in `features/habit/domain/templates.dart`:
`drinkWater` (count 8 glasses), `read` (count 20 pages), `walk` (count 30 minutes), `meditate`
(count 10 minutes), `wakeUpEarly` (yes/no), `study` (count 60 minutes), all daily, with fixed icon
and color keys from the shared 16-color set. Names and units are ARB keys (`habit_template_*`,
`habit_unit_*`); HAB-02 resolves them and saves the shown text as typed (spec Assumptions). Name
suggestions match the typed text against the localized template names.

**Rationale**: spec §12 ("habit templates are l10n keys"); presentation stays the only place with
`BuildContext`.

## R17. Settings and seeding

**Decision**: one new `AppSettings` field, `habitRemindersEnabled` (default true, key
`habitRemindersEnabled`; SET-01 toggle in T3.1). No seed data for habits. Backup excludes nothing new
until T3.2, which must include the 3 habit tables and this key (Open item).

## R18. Testing strategy specifics

- **Unit (domain)**: `StreakEngine` (R6 table + oracle ≥ 100 histories), `FreezePolicy`,
  `planReminders` (every schedule type × done/not done × only-if-not-done on/off × before/after the
  reminder time × week target met × start date in future), milestone selection, `validateHabit`,
  `LocalDate`.
- **Unit (data)**: real in-memory Drift — repository CRUD, soft delete cascade, one physical entry row
  per day (toggle 10× → 1 row), schedule versions on same-day edits, compare-and-set milestones under
  two concurrent writers, freeze cap, migration v1/v2/v3 → v4 with data.
- **Widget**: every HAB-01/02/03 acceptance criterion and derived scenario with fake repositories,
  `FakeNotificationService`, `FakeImageSharer`, `FakeFeatureGate`, `NoAdsService`, and `MutableClock`.
- **Golden (Linux)**: HAB-01 light/dark × English/Gujarati (Constitution IV); also HAB-03 and the
  milestone sheet in light/dark English.
- **Performance**: heatmap builder 365 days < 100 ms; HAB-01 first content < 500 ms at 50 habits × 5
  years; day write + engine < 100 ms (host stand-ins, same thresholds, like feature 003).
- **Integration**: create habit → check in → streak shows 1 → back-fill yesterday (§13).
- **Device (manual)**: reminder at set time; after reboot; "only if not done" suppression; exact vs
  inexact; share sheet with the image.
